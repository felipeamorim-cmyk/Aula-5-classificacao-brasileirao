Bloco 1 — Da Regressão à Classificação

Por que não usar a reta da regressão linear?

Se usássemos uma reta para prever vitória do mandante, o modelo poderia responder \(+2.5\) ou \(-0.4\)…

…mas probabilidade só existe entre \(0\) (0%) e \(1\) (100%).

Precisamos de uma função que “esprema” qualquer número real para o intervalo \([0, 1]\).

A Função Sigmoide — símbolo por símbolo

\[\sigma(z) = \frac{1}{1 + e^{-z}}\]

Símbolo O que é Intuição
\(z\) O “placar interno” do modelo (pode ser qualquer número de \(-\infty\) a \(+\infty\)) Quanto maior \(z\), mais o modelo “acredita” na vitória do mandante
\(e\) Constante de Euler (\(\approx 2.718\)) Motor do crescimento/decaimento exponencial
\(e^{-z}\) Decai quando \(z\) cresce É o mecanismo do “espremedor”
\(\sigma(z)\) A saída: probabilidade entre 0 e 1 Nossa previsão final

A Função Sigmoide — nos extremos

\[\sigma(z) = \frac{1}{1 + e^{-z}}\]

  • \(z \to +\infty \Rightarrow e^{-z} \to 0 \Rightarrow \sigma \to \frac{1}{1+0} = 1\) (100%)
  • \(z \to -\infty \Rightarrow e^{-z} \to +\infty \Rightarrow \sigma \to \frac{1}{1+\infty} = 0\) (0%)
  • \(z = 0 \Rightarrow \sigma = \frac{1}{1+1} = 0.5\) (moeda ao ar: total indecisão)

A sigmoide nunca toca 0 ou 1 — o modelo nunca tem certeza absoluta.

A sigmoide desenhada

A sigmoide em ação: features × pesos → probabilidade

Como um jogo vira um ponto na curva:

  • Os \(x\) são as features do jogo: o time é mandante? qual a forma recente (quantos jogos venceu ultimamente)? qual o saldo de força?
  • Os \(\beta\) são os pesos: o quanto cada feature importa. Nem tudo importa igual! Um time de grande história, como o Vasco, mas em fase ruim, recebe peso menor na forma recente do que Flamengo e Palmeiras, que vivem grande momento.
  • Cada \(\beta_j \cdot x_j\) empurra o placar \(z\) um pouco; a soma total entra na sigmoide e vira o ponto vermelho: a probabilidade final.

A sigmoide em ação: o gráfico

De onde vem o \(z\)? A combinação linear

\[z = \beta_0 + \beta_1 \cdot x_1 + \beta_2 \cdot x_2 + \dots \]\[z = \beta_0 + \beta_1 \cdot x_1 + \beta_2 \cdot x_2 + \dots\]

Símbolo O que é No futebol
\(x_1, x_2, \dots\) As variáveis (features) que descrevem o jogo Saldo de força, saldo de gols, momento…
\(\beta_1, \beta_2, \dots\) Os pesos que o algoritmo aprende Quanto cada variável empurra o placar a favor (ou contra)
\(\beta_0\) O intercepto: o valor de \(z\) quando tudo é zero Times iguais jogando → o que sobra é a vantagem de jogar em casa

Regressão Logística = combinação linear + sigmoide: \(P(\text{vitória}) = \sigma(\beta_0 + \beta_1 x_1 + \dots)\)

E os jogos adiados (remarcados)?

No Brasileirão real, jogos são adiados (copas, datas FIFA, logística). No nosso dataset eles aparecem de duas formas:

  1. Jogos remarcados já realizados: entram pela data em que de fato foram jogados, não pela rodada original. Como nosso split usa o calendário real (arrange(date) + initial_time_split), eles caem automaticamente do lado certo da divisão — sem ajuste manual. ✅
  2. Jogos sem data definida (3 jogos com date vazia e score == "x"): ainda não aconteceram, então ficam fora de treino e teste — aparecem só na previsão do futuro, no fim da aula.

Tip

Se o split fosse por número da rodada em vez da data, um jogo adiado da rodada 3 jogado em agosto entraria no treino “como se” tivesse acontecido em janeiro — vazamento sutil. Dividir pela data real evita isso.

A função que monta o saldo de forças

add_features <- function(df, ratings) {
  df |>
    left_join(ratings, by = c("home" = "time")) |>      # ← aproveitamento do mandante
    rename(ap_home = aproveitamento) |>
    left_join(ratings, by = c("away" = "time")) |>      # ← aproveitamento do visitante
    rename(ap_away = aproveitamento) |>
    mutate(saldo_forca = ap_home - ap_away)             # ← a feature do modelo
}

Bloco 2 — Log-Loss: como o modelo aprende

Por que não usar o MSE?

Na regressão linear, minimizávamos o erro quadrático médio (MSE).

Em classificação probabilística, usamos a Log-Loss (entropia cruzada / deviance):

\[\text{LogLoss} = -\frac{1}{n} \sum_{i=1}^{n} \Big[ \; y_i \log(p_i) + (1 - y_i)\log(1 - p_i) \; \Big]\]

Símbolo O que é
\(n\) Número de jogos
\(y_i\) O que aconteceu no jogo \(i\): 1 = mandante venceu, 0 = não
\(p_i\) O que o modelo previu: probabilidade de vitória do mandante
\(\log\) Logaritmo natural — transforma multiplicações de probabilidades em somas

A mágica da fórmula: só um termo “sobrevive”

\[\text{LogLoss} = -\frac{1}{n} \sum_{i=1}^{n} \Big[ \; y_i \log(p_i) + (1 - y_i)\log(1 - p_i) \; \Big]\]

Para cada jogo, apenas um dos dois termos conta:

  • Se o mandante venceu (\(y_i = 1\)): o custo é \(-\log(p_i)\) → o modelo é punido se deu pouca chance à vitória
  • Se o mandante não venceu (\(y_i = 0\)): o custo é \(-\log(1 - p_i)\) → o modelo é punido se deu chance demais à vitória

E quanto mais confiante e errado o palpite, maior a punição ↓

A punição pela arrogância

O efeito no aprendizado

Flamengo em casa, modelo crava 99% de chance, e o time perde:

\[-\log(1 - 0.99) = -\log(0.01) \approx 4.6\]

Se tivesse cravado 99,9%: \(-\log(0.001) \approx 6.9\)

A Log-Loss obriga o modelo a calibrar probabilidades realistas — quem dá palpite exagerado paga caro. É por isso que a Regressão Logística é conhecida por gerar probabilidades bem calibradas.

Ajustando a Regressão Logística

Como ler cada coluna:

  • β estimado → o peso aprendido nos dados de treino (a “receita” do modelo)
  • Erro-padrão → a margem de incerteza do β
  • Estatística z (−4.66 aqui) → β ÷ erro-padrão, uma razão sinal/ruído: \(|z| > 2\) já indica que a variável carrega sinal real, longe do acaso
  • p-valor → probabilidade de ver um sinal desse tamanho se o β fosse zero de verdade (aqui ≈ 0,000003 → o saldo de força importa mesmo)

Note

O β aparece negativo porque o glm, internamente, modela a probabilidade do segundo nível do fator (“nao”). O parsnip desfaz a inversão nas previsões — para nós, o evento é sempre o 1º nível (“sim”).

Os coeficientes na prática (1): a receita do modelo

Desfazendo a inversão do glm, a receita aprendida no treino é:

\[P(\text{vitória}) = \sigma\Big(\;\underbrace{0.05}_{\beta_0:\ \text{ponto de partida}} + \underbrace{4.37}_{\beta_1:\ \text{peso do saldo}} \times \text{saldo\_forca}\;\Big)\]

Lendo em português claro:

  • β₀ = 0.05 → se os times têm força igual (saldo = 0), o placar interno é quase zero e \(\sigma(0) \approx 50\%\): o mando de campo, sozinho, vale pouco mais que uma moeda ao ar
  • β₁ = 4.37 → cada ponto de saldo de força empurra o placar \(z\) 4.37 unidades para cima (mais chance de vitória)

Os coeficientes na prática (2): calculando na mão

Exemplo real do nosso campeonato — Flamengo (ap = 0.685) recebe a Chapecoense (ap = 0.167):

Passo Conta Resultado
1️⃣ Saldo de força \(0.685 - 0.167\) \(0.518\)
2️⃣ Placar interno \(z = 0.05 + 4.37 \times 0.518\) \(z \approx 2.3\)
3️⃣ Sigmoide \(\sigma(2.3) = \frac{1}{1 + e^{-2.3}}\) \(\approx 0.91\) → 91% de chance

E se fossem dois times iguais? saldo = 0 → \(z = 0.05\) → \(\sigma \approx 51\%\): só o mando de campo.

É exatamente assim que o modelo transforma “quem está melhor no campeonato” em probabilidade.

Os quatro cenários

Real: venceu ✅ Real: não venceu ❌
Previu: vence ✅ TP — acertou o palpite ⚠️ FP — alarme falso
Previu: não vence ⚠️ FN — deixou passar ✅ TN — acertou o palpite

Como ler a matriz:

  • Precisão → olha a linha de cima → → → (“dos meus palpites de vitória, quantos certos?”)
  • Recall → olha a coluna da esquerda ↓ ↓ ↓ (“das vitórias reais, quantas capturei?”)

Bloco 4 — Métricas do Analista

As fórmulas, símbolo por símbolo

Métrica Fórmula Pergunta de negócio Onde olhar na matriz
Precisão \(\frac{TP}{TP + FP}\) Dos palpites de vitória, quantos se confirmaram? Linha →
Recall \(\frac{TP}{TP + FN}\) Das vitórias reais, quantas capturamos? Coluna ↓
F1-Score \(2 \cdot \frac{P \cdot R}{P + R}\) Equilíbrio entre as duas (média harmônica) Diagonal
Kappa \(\frac{p_o - p_e}{1 - p_e}\) Quanto melhor que um chute ponderado pelo acaso? Toda ela

Onde \(p_o\) = concordância observada (acurácia) e \(p_e\) = concordância esperada pelo acaso, dadas as proporções das classes.

Quando cada uma importa

  • Precisão → apostador/investidor: cada falso positivo é dinheiro perdido num palpite errado. Alarme falso custa caro.
  • Recall → fraude/saúde: cada falso negativo é um caso real que passou despercebido. Deixar passar é inaceitável.
  • F1 → quando as duas frentes importam; penaliza modelos que sacrificam uma pela outra.
  • Kappa → responde: “meu modelo é melhor que um chute que respeita as proporções do campeonato?” \(\kappa \approx 0\) = não.

Exemplo visual: 10 palpites

Antes dos dados reais, vamos ver as métricas nascendo num campeonato de brinquedo com 10 jogos:

E as outras duas saem da mesma contagem: Acurácia = (4 TP + 2 TN)/10 = 60% · F1 = média harmônica de 80% e 57% ≈ 67%.

Bloco 5 — Cutoff, Curva ROC e Fechamento

O limiar de decisão (cutoff)

Por padrão: \(p \geq 0.50\) → “vence”.

Subindo o corte para 0.65, só cravamos vitória com mais confiança:

  • modelo fica conservador → menos palpites de vitória
  • precisão ↑ (os poucos palpites são mais certeiros)
  • recall ↓ (deixamos escapar mais vitórias reais)
comparar_cutoffs <- function(limiar) {
  teste_pred |>
    mutate(pred = factor(if_else(.pred_sim >= limiar, "sim", "nao"),  # ← aplica o corte
                         levels = c("sim", "nao"))) |>
    metric_set(accuracy, precision, recall, f_meas)(truth = home_win, estimate = pred) |>
    mutate(cutoff = limiar)
}

bind_rows(comparar_cutoffs(0.5), comparar_cutoffs(0.65)) |>   # ← compara os dois limiares
  pivot_wider(names_from = cutoff, values_from = .estimate, names_prefix = "cut_")

Curva ROC e AUROC

Em vez de escolher um corte, a Curva ROC testa todos os cortes ao mesmo tempo:

  • Eixo y: taxa de verdadeiros positivos (recall) ↑
  • Eixo x: taxa de falsos positivos →
  • AUROC (área sob a curva): 0.5 = chute aleatório · 1.0 = separação perfeita

Bloco 6 — Validação Cruzada e Regularização

O problema com um único split

Nosso teste tem só 64 jogos → as métricas oscilam bastante por acaso.

Solução: validação cruzada. Mas com dados temporais, o CV clássico (k-fold aleatório) vaza informação do futuro…

✅ CV temporal (janela deslizante): cada fatia treina no passado e valida no futuro imediato:

Mais features para o Lasso fazer sentido

Regularizar uma variável não faz sentido. Vamos dar ao modelo três saldos — e deixar o Lasso decidir quais valem a pena:

stats_home <- treino |> group_by(time = home) |>
  summarise(jogos = n(), pontos = sum(3 * (gols_home > gols_away) + (gols_home == gols_away)),
            gm = sum(gols_home), gs = sum(gols_away))          # ← gols marcados/sofridos
stats_away <- treino |> group_by(time = away) |>
  summarise(jogos = n(), pontos = sum(3 * (gols_away > gols_home) + (gols_away == gols_home)),
            gm = sum(gols_away), gs = sum(gols_home))

ratings2 <- full_join(stats_home, stats_away, by = "time") |>
  mutate(across(-time, ~ replace_na(.x, 0))) |>
  transmute(time,
            aproveitamento = (pontos.x + pontos.y) / (3 * (jogos.x + jogos.y)),
            gm_medio = (gm.x + gm.y) / (jogos.x + jogos.y),
            gs_medio = (gs.x + gs.y) / (jogos.x + jogos.y))

Três features de saldo

add_features2 <- function(df, ratings) {
  df |>
    left_join(ratings, by = c("home" = "time")) |>
    rename_with(~ paste0(.x, "_home"), c(aproveitamento, gm_medio, gs_medio)) |>
    left_join(ratings, by = c("away" = "time")) |>
    rename_with(~ paste0(.x, "_away"), c(aproveitamento, gm_medio, gs_medio)) |>
    mutate(
      saldo_forca  = aproveitamento_home - aproveitamento_away,  # ← quem está melhor
      saldo_ataque = gm_medio_home - gm_medio_away,              # ← quem marca mais
      saldo_defesa = gs_medio_away - gs_medio_home               # ← quem sofre menos
    )
}

Regularização Lasso — a ideia

A Log-Loss sozinha pode superajustar (decorar o treino). O Lasso (L1) adiciona um pedágio por coeficiente grande:

\[\min_{\beta} \;\; \underbrace{\text{LogLoss}(\beta)}_{\text{acertar o treino}} + \;\; \lambda \underbrace{\sum_j |\beta_j|}_{\text{pedágio por complexidade}}\]

Símbolo O que é
\(\lambda\) Intensidade da penalização — nosso hiperparâmetro a otimizar
\(\sum_j \vert\beta_j\vert\) Soma dos tamanhos dos pesos (norma L1)

A norma L1 tem uma propriedade famosa: ela zera coeficientes de variáveis que não carregam sua parte do pedágio → seleção automática de features.

Como o modelo prevê o fim do campeonato?

Somando os pontos já conquistados com os pontos dos jogos futuros segundo a decisão do modelo (\(p \geq 0.5\) → vitória do mandante; senão, vitória do visitante):

# pontos já conquistados nos jogos realizados
pts_home <- jogos |>
  mutate(p = case_when(gols_home > gols_away ~ 3, gols_home == gols_away ~ 1, TRUE ~ 0)) |>
  count(time = home, wt = p, name = "pontos")            # ← pontos como mandante
pts_away <- jogos |>
  mutate(p = case_when(gols_away > gols_home ~ 3, gols_away == gols_home ~ 1, TRUE ~ 0)) |>
  count(time = away, wt = p, name = "pontos")            # ← pontos como visitante

tabela_atual <- full_join(pts_home, pts_away, by = "time") |>
  transmute(time, pontos_atuais = pontos.x + pontos.y)

# decisão do modelo em cada jogo futuro
fut_pred <- predict(fit_lasso, new_data = futuro, type = "prob") |>
  bind_cols(futuro)

prev_home <- fut_pred |> filter(.pred_sim >= 0.5) |>
  count(time = home, wt = 3, name = "prev")              # ← 3 pts por vitória prevista em casa
prev_away <- fut_pred |> filter(.pred_sim < 0.5) |>
  count(time = away, wt = 3, name = "prev")              # ← 3 pts por vitória prevista fora

tabela_final <- tabela_atual |>
  full_join(prev_home, by = "time") |>
  full_join(prev_away, by = "time") |>
  mutate(across(-time, ~ replace_na(.x, 0))) |>
  transmute(time,
            pontos_atuais,
            pontos_previstos = prev.x + prev.y,

Limitações desta projeção

Nosso modelo é binário: ele não prevê empates — cada jogo futuro vira 3 pontos para alguém, então os totais ficam inflados em relação à realidade. Some-se a isso os ratings congelados no treino. É uma projeção didática, não um palpite para apostas!

Resumo da aula

  1. Sigmoide espreme o placar linear \(z\) para \([0,1]\) → probabilidade
  2. Log-Loss pune arrogância → probabilidades calibradas
  3. Acurácia mente em classes assimétricas → matriz de confusão
  4. Precisão / Recall / F1 / Kappa → cada uma responde a um custo de negócio
  5. Cutoff e ROC-AUC → o ponto de corte é uma decisão nossa, não do modelo
  6. CV temporal + Lasso → comparar modelos sem contaminar o teste, e deixar a regularização podar o que não agrega
